# 固定公司面试准备文档

产品方向：面试准备提供全面、可自行安排和并行处理的材料，而非飞书消息带练。此文档优先于旧规划中的单焦点、5/10/5 分钟步骤与准备任务设计。降低注意力成本靠减少检索与协调，不限制用户同时推进多个岗位。

## 通用复习材料与公司资料的分工

通用基础、Agent/Harness、全栈、系统设计和个人项目解释只准备一份完整讲义，不按每家公司反复扩写。固定入口写在 `config/interview-guide.json` 的 `url`（形如 https://example.feishu.cn/docx/REPLACE_ME，换成你自己的讲义链接；本地副本可另写 `local_entry`），工作台的「面试准备」块和执行器提示词都从这里取。

某家公司的材料达到要求后，有实际新回复、改期、轮次、复盘或相关公司实质变化时再补改。定时核查没有新事实时只记核查时间，不添加通用题目，不重复通知。新公司资料需要基础和项目知识时引用这份讲义，保留公司特有信息、面经证据与轮次记录。

## 文档内容与证据

每家公司保留唯一 `lead.interview_dossier.document_id` 和固定 URL。内容至少包括面试事实概览、可并行准备清单、公司产品、带日期的近期动态、面经与候选人反馈的证据状态、通用复习讲义链接及与该岗位直接相关的项目证据、反问与择业判断、历轮进展、用户笔记和维护记录。

官方产品文档/更新日志、招聘方邮件与当前 JD 优先。面经记录作者、时间、岗位、轮次和原始链接；招聘方采访不是候选人面经，自动生成题库不是实际考题。找不到第一手面经就明确写检索范围和缺口。旧宣传、岗位海报、相对日期和历史待遇不得当作当前事实。技术题和架构建议标明为推断/通用准备。个人贡献服从 candidate/facts.yaml，参与或集成类工作不夸成算法或后端独立所有权。

## 创建与更新

1. `prepare-interviews` 比较岗位、JD、时间、轮次、面试官、新回复和复盘的输入 hash。无文档、输入变化，或面试前三天超过 24 小时未核查资料时，幂等生成 `research_interview_dossier` 宿主任务。
2. 宿主使用 lark-doc 技能检索和创作。已有 document_id 时先 fetch 当前内容及评论，只补改相关段落；保留用户笔记、勾选与资源，不整篇覆盖。没有变化只更新 researched_at，保留 content_hash，不制造更新消息。
3. 创建成功立刻把返回的 document_id 和 URL 保存到该任务的证据文件，禁止重试时再次创建。同一公司跨轮次仍使用同一文档。
4. 将登记 JSON 存于 runs/interviews：record_id、document_id、url、summary、researched_at、input_hash（调用 dossierInputHash）、content_hash（仅实质内容改变时更新）、sources（url/title/checked_at）和可选 local_path。
5. 执行 `node bin/register-dossier.mjs --input runs/interviews/…-receipt.json`。它重新 fetch 文档验证公司与正文、拒绝替换已有文档 ID、拒绝以过期输入登记，再保存 published 回执并关闭关联资料任务。不能只根据生成本地 Markdown 就记为完成。
6. `project-journey` 把准备文档入口写入飞书表格面试记录；`concierge` 发固定文档链接。内容实质更新通知一次；无变化不重复催促。

用户直接在文档中写的新面经，由定时宿主在资料核查时读取；在机器人发送“编号 复盘 …”会立即保存原文，并排队更新资料。当前不是对所有文档编辑实时监听。

## 公司调研与「怎么准备」（Judge，决定之前就有）

固定文档是面试阶段的深度版；判断线索的时候先有两样轻的，都在线索详情页顶上，指挥台的申请抽屉里有公司小卡：

- **公司调研**：一家公司一份，这家公司的岗位共用，存 `state/company-briefs/<公司键>.json`。摘要两三句；业务、规模 / 融资 / 阶段、在哪招、技术与 AI 方向、带日期的近期动态、口碑（加班、点评）、面试流程与面经要点、公开的薪资信号、风险、来源。每条说法引用来源序号，来源有标题、链接、日期；二手来源（牛客、看准、脉脉、知乎等）撑不起业务、规模、新闻和摘要，页面上标「二手」。查不到公开资料就记下查过哪里（`status: not_found`），30 天内不自动重查。
- **怎么准备**：一条线索一份，存 `state/role-prep/<线索 id>.json`。由公司调研、JD 和判断的主要缺口推出三小节：补一补、准备讲（用真实经历）、这家公司（面经要点）；补一补和准备讲每条引用它回应的 JD 原文。有固定文档时页面上链过去。

写入只走 `node bin/company.mjs`（`template`、`show`、`brief`、`prep-input`、`prep`、`request`；`--check` 只校验）：缺来源、格式不对、JD 引文不在 JD 里整份拒收并逐条说怎么改。写入成功把开着的对应任务记为完成；`node bin/job.mjs done` 在写入之前拒收这两种任务。

排队由 Judge 在周期尾段做（`prepare-interviews`）：`company_brief` 给新线索 / 待批准里推荐或待核的公司（还有走到递出、等着写「怎么准备」的公司），没有调研或调研满 30 天才排，同时开着的自动调研不超过 `config/pipeline.json` 的 `company_briefs.per_cycle`（默认 5），岗位多的公司先；`role_prep` 给走到递出及以后、有 JD 的线索，公司调研好了（或公司不明、查不到）才排，同时最多 `company_briefs.prep_per_cycle`（默认 5）条。页面上的「调研这家公司」「生成怎么准备」立刻排队并拉起即时执行器，不占名额。

## 当前实际文档（示例格式）

每家在面公司在这里记一条，例如：

- Example Corp（申请 <岗位>，面试官 <角色>）：https://example.feishu.cn/docx/REPLACE_ME
- 当前面试：<日期>（<星期>）<时间> Asia/Shanghai；会议入口 <会议链接>。语言和现场编程形式未说明。改期后不再按旧日期提醒。
- 改期证据：runs/<日期>/<公司>-confirmed-invite.json；固定文档已更新并回读。后续以 state/leads.ndjson 和新的实际邀请为准。
- 初稿与外部回执：runs/interviews/<公司>-dossier.xml、<公司>-document-created.json、<编号>-document-readback.json。

固定链接属于求职资料，不对招聘方自动共享。消息不发送模拟题、启动训练或逐步打卡。原生任务仅保留真实面试时间提醒；旧准备任务标记停用后关闭，不能把这次产品迁移记成用户已准备完成。
